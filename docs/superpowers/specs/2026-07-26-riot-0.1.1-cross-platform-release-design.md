# Riot 0.1.1 Cross-Platform Release Design

**Date:** 2026-07-26  
**Status:** Approved in conversation; pending metaswarm design review  
**Target branch:** `chore/release-0.1.1-final` from merged `main`  
**Bundle/application ID:** `net.protest.riot`

## Goal

Release one reviewable Riot 0.1.1 candidate across the supported public
channels:

- iPhone and iPad through TestFlight;
- macOS through TestFlight/App Store Connect;
- macOS direct download through a notarized, stapled DMG on GitHub;
- Android production through Google Play; and
- Android direct download through a signed APK on GitHub.

The release also replaces the current raised-fist icon with the selected
flower-thrower artwork on all three platforms and deploys a public support page
at `https://riot.protest.net/support/`.

## Definition of Done

1. The icon and support-page changes are committed, independently reviewed,
   green under every mandatory repository gate, merged to `main`, and built
   only from the clean merge commit.
2. The live support URL returns 200 and names `support@protest.net`.
3. The signed Android release APK installs and launches without native/FFI
   loading errors.
4. A signed Android AAB and APK contain the intended launcher icon and exact
   upload certificate.
5. A signed iOS 0.1.1 build with the intended icon is accepted by App Store
   Connect for TestFlight processing.
6. A signed macOS 0.1.1 App Store package with the intended icon is accepted by
   App Store Connect for TestFlight processing.
7. The direct-download macOS app and DMG are notarized, stapled, and accepted
   by Gatekeeper.
8. GitHub release `v0.1.1` publishes the notarized DMG and signed APK, but no
   store-only IPA, PKG, or AAB.
9. The Google Play production record is either submitted with the exact
   candidate AAB or handed to the owner at the first authenticated/legal
   Console gate with every field and artifact prepared.

## Approved Product Decisions

- Marketing version remains `0.1.1`; only build/version codes increase.
- Store name is `riot.protest.net`; installed application label remains `Riot`.
- The application is free, worldwide, public early access.
- Store category is Social / Social Networking.
- Content rating is the Teen-equivalent result produced by the existing
  release worksheet.
- Public support contact is `support@protest.net`.
- Privacy URL is `https://riot.protest.net/privacy/`.
- Support URL is `https://riot.protest.net/support/`.
- The first Google Play submission targets production, not a test track.
- macOS ships through both App Store Connect/TestFlight and a notarized GitHub
  DMG.
- The selected icon is the flower-thrower asset already prepared in
  `/Users/rabble/code/explorations/riot-wt-icon`.

## Artwork Risk Decision

The selected icon closely reproduces recognizable Banksy flower-thrower
artwork. This creates avoidable copyright, trademark, store-review, and future
replacement risk. The owner selected this icon after the risk was presented.
The repository and release notes must not claim ownership or a license that has
not been evidenced. A store rejection on this ground is not grounds to bypass
review; the recovery is an original replacement icon and a new build.

## Scope

### In scope

- Replace the iOS 1024-point AppIcon source.
- Regenerate the macOS `.icns` from the selected source.
- Add Android legacy, round, adaptive, foreground, and monochrome launcher
  assets for all shipped density buckets.
- Wire `android:icon` and `android:roundIcon` in the application manifest.
- Add byte-identical source/deployment support pages under `marketing/` and
  `marketing/public/`.
- Add the support route to the sitemap, live verifier, site documentation, and
  route/mirror contracts.
- Link support from site footers and the privacy/releases surfaces without
  promoting it into primary navigation.
- Update release documentation and canonical listing material where necessary.
- Build, sign, verify, upload, notarize, deploy, and publish the approved
  artifacts.

### Out of scope

- Changing application behavior unrelated to the icon or release.
- Bumping the marketing version to 0.1.2.
- Completing or merging the broader unfinished public-store-release-kit branch.
- Claiming legal ownership of third-party artwork.
- Accepting store contracts, export classifications, content-rating
  attestations, or other legally attributable declarations for the owner.
- Publishing an unnotarized DMG or an unlaunched Android release.

## Source Isolation and Candidate Identity

Implementation occurs in an isolated branch/worktree created from merged
`main`. The existing `riot-wt-icon` changes are source material only; they are
copied into the new branch after tests establish the expected contracts.
Nothing is committed in the dirty main checkout or directly in another
agent's worktree.

The final release candidate is the merge commit of the implementation PR. All
release scripts run without `ALLOW_DIRTY=1`. The scripts derive Apple build
numbers and Android `versionCode` from that commit count, so all artifacts
identify the same source state.

## Components

### 1. Cross-platform icon set

The canonical visual source is the selected 1024×1024 RGB PNG from the icon
worktree. Platform outputs are:

- `apps/ios/Riot/Assets.xcassets/AppIcon.appiconset/AppIcon-1024.png`;
- `apps/macos/Riot/AppIcon.icns`;
- Android `mipmap-{mdpi,hdpi,xhdpi,xxhdpi,xxxhdpi}` legacy, round, and
  foreground PNGs;
- Android adaptive icon XML under `mipmap-anydpi-v26`; and
- Android launcher background color resources.

Android manifest references must resolve for both regular and round launchers.
Adaptive foreground and monochrome declarations use the same prepared
foreground asset. Tests inspect resource existence, image dimensions, manifest
references, and adaptive-icon XML before Gradle packaging is allowed.

### 2. Public support surface

`marketing/support/index.html` is the editorial source.
`marketing/public/support/index.html` is its byte-identical deployment mirror.
The page provides:

  incident details in public reports;

The sitemap, README, live verifier, route inventory, footer contracts, and

### 5. Delivery coordinator

There is no new monolithic release program. Existing small tools remain
responsible for one boundary:

- marketing tests and Wrangler own support deployment;
- `scripts/android-release.sh` owns Android build/signature verification;
- `scripts/testflight-release.sh` owns iOS archive/export/upload;
- `scripts/macos-release.sh` owns Mac App Store and Developer ID channels;
- `gh release` owns GitHub assets; and
- Play Console owns the first Android app record and legal declarations.

This preserves independently understandable failure boundaries.

## Release Data Flow

1. Approved source changes merge to `main`.
2. A clean release worktree checks out the merge commit.
3. Marketing tests pass; Wrangler deploys the exact `marketing/public` tree.
4. Live verification proves `/support/` and all other routes.
5. Android release script generates net-enabled bindings and both native ABIs,
   then Gradle builds and signs AAB/APK.
6. Signature and icon checks pass; the APK is installed and launched; logs are
   checked for FFI/native load failures.
7. iOS release script regenerates net-enabled bindings/native core, archives,
   exports, validates icon/signing, and uploads the IPA.
8. macOS App Store channel builds the universal binary, archives, exports, and
   uploads the PKG.
9. macOS Developer ID channel builds the same source, notarizes the app and
   DMG, staples both, and verifies Gatekeeper acceptance.
10. GitHub release publishes the DMG and APK with checksums and release notes.
11. The owner completes the Play Console creation/legal gate; the exact AAB and
    canonical listing are submitted to production.

## Test-Driven Development

Tests are written and observed failing before asset/page implementation:

1. A release contract test requires Android manifest launcher references,
   every density asset, adaptive/round XML, and valid dimensions.
2. Marketing contracts require `/support/`, exact source/public bytes,
   support-email/privacy/GitHub links, updated footers, and the ten-route
   sitemap/live inventory.
3. Existing marketing tests remain the accessibility, dependency, remote
   request, cookie, mirror, and route guardrails.

After implementation:

- targeted release and marketing tests pass;
- Android host-JVM tests and lint pass;
- shell syntax and ShellCheck pass for release entry points;
- Rust fmt, Clippy, workspace tests, contract validation, and the exact
  composite coverage gate pass;
- the mandatory independent review reports no Critical or Important findings;
  and
- CI passes on the PR before merge.

## Artifact Verification

### Android

- Confirm AAB and APK exist.
- Verify APK signature and exact certificate SHA-256.
- Verify AAB JAR signature and exact certificate SHA-256.
- Inspect packaged launcher resources.
- Install the release APK on a clean emulator or attached device.
- Launch the main activity and inspect logs for missing library, UniFFI symbol,
  signature, and startup exceptions.

### iOS

- Confirm archive/export success and App Store provisioning.
- Inspect the archived asset catalog/application metadata for the selected
  icon.
- Validate/upload the IPA with App Store Connect credentials.
- Record delivery/build identifiers and processing status without claiming
  TestFlight availability before Apple processes the build.

### macOS App Store

- Confirm universal arm64/x86_64 app binary.
- Confirm App Store distribution and installer signing.
- Confirm category and dSYM.
- Inspect the archived `.icns`.
- Validate/upload the PKG and record delivery status.

### macOS direct download

- Confirm Developer ID signing and hardened runtime.
- Notarize and staple the app before packaging.
- Build, notarize, and staple the DMG.
- Run `spctl`, `codesign`, `stapler`, and architecture verification.
- Never publish a DMG whose notarization or Gatekeeper check is incomplete.

## External and Human Gates

### Apple

Binary upload and notarization are automated. App Store Connect may still
require export-compliance, beta-review, agreements, tax, trader-status, or
other account-owner actions. Those are reported with the exact screen/status;
they are not guessed or accepted by automation.

### Google Play

Google requires the initial app record to be created in Play Console. The
current machine has an active `gcloud` user but no Play-linked service account
or Android Publisher credentials. Therefore the implementation prepares every
artifact and field but does not pretend that generic Google Cloud
authentication can create or publish the Play application.

The owner must:

1. create the free app record for `riot.protest.net`;
2. accept Play App Signing and legal declarations;
3. confirm content rating, data safety, target audience, and availability; and
4. upload/submit the supplied production AAB, or link a service account with
   production release permission for subsequent automation.

## Failure Handling and Recovery

- Dirty tree: stop; rebuild from the merged commit.
- Shared release lock exists: stop; identify the active/stale owner before
  removal.
- Icon contract fails: stop; regenerate from the canonical source.
- Support deployment/live verification fails: stop before store submission.
- Signing identity/certificate mismatch: stop; never resign with a new key.
- APK install/launch fails: diagnose the release binary; do not submit AAB.
- Apple upload rejected: retain the exact archive and delivery log; fix root
  cause in a new reviewed commit/build.
- Apple processing or legal gate pending: report pending, not released.
- Notarization or Gatekeeper failure: do not publish the DMG.
- Existing GitHub `v0.1.1`: inspect and update intentionally; never create a
  duplicate or overwrite unrelated assets.
- Play Console blocks submission: preserve the exact AAB and prefilled
  worksheet; hand off the precise unresolved human action.

## Release Evidence

The final handoff records:

- source merge commit;
- version/build numbers;
- artifact paths, sizes, and SHA-256 checksums;
- Apple delivery/notarization identifiers and states;
- Android signing certificate fingerprint;
- APK install/launch evidence;
- live support URL verification;
- GitHub release URL and asset names;
- Play Console state and exact remaining human action; and
- all red/green test history relevant to the candidate.
