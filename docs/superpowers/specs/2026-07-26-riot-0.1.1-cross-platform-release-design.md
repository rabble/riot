# Riot 0.1.1 Cross-Platform Release Design

**Date:** 2026-07-26

**Status:** Approved in conversation; metaswarm review round 1 revisions applied

**Target branch:** `chore/release-0.1.1-final` from merged `main`

**Bundle/application ID:** `net.protest.riot`

## Goal

Release one reviewable Riot 0.1.1 candidate across the supported public
channels:

- iPhone and iPad through TestFlight;
- macOS through TestFlight/App Store Connect;
- macOS direct download through a notarized, stapled DMG on GitHub;
- Android production through Google Play; and
- Android direct download through a signed APK on GitHub.

The release also replaces the current raised-fist icon with the selected
flower-thrower artwork on all three platforms and deploys a public support page
at `https://riot.protest.net/support/`.

## Users and Release Use Cases

- **A TestFlight tester** wants one clearly identified iOS/macOS 0.1.1 build so
  that feedback refers to the same reviewed source, when the build finishes
  App Store Connect processing.
- **An Android user** wants a production Play install and a verifiably
  compatible direct-download APK so that switching distribution channels does
  not strand their installed data, when Play has produced the signed delivery
  artifact.
- **A direct-download Mac user** wants a notarized, Gatekeeper-accepted DMG so
  that Riot installs without bypassing platform security, when GitHub release
  `v0.1.1` is published.
- **A person who needs help** wants a private email route and a clearly
  separated public bug-report route so that sensitive material is not posted
  publicly, when they visit the site or a store listing.
- **The release owner** wants exact provenance, channel state, and rollback
  evidence so that a bad release can be contained without guessing, during the
  first 24 hours after each public channel begins serving the build.

The MVP is the icon, support/release surfaces, complete store-listing package,
signed candidates, clean-source provenance, required uploads, and truthful
handoff at owner-only gates. Additional listing experiments and visual polish
after store acceptance are follow-up work.

## Definition of Done

1. The icon and support-page changes are committed, independently reviewed,
   green under every mandatory repository gate, merged to `main`, and built
   only from the clean merge commit.
2. The live support URL returns 200 and names `support@protest.net`.
3. The locally signed smoke-test APK and Play-signed universal APK both install
   and launch without native/FFI loading errors.
4. The AAB and local smoke-test APK contain the intended launcher icon and
   exact upload certificate; the public APK contains the intended icon and
   exact Play app-signing certificate.
5. A signed iOS 0.1.1 build with the intended icon is accepted by App Store
   Connect for TestFlight processing.
6. A signed macOS 0.1.1 App Store package with the intended icon is accepted by
   App Store Connect for TestFlight processing.
7. The direct-download macOS app and DMG are notarized, stapled, and accepted
   by Gatekeeper.
8. GitHub release `v0.1.1` publishes the notarized DMG and Play-signed
   universal APK, but no local smoke-test APK, IPA, PKG, or AAB.
9. The Google Play production record is submitted with the exact candidate
   AAB. If an authenticated/legal Console gate blocks that action, the owner
   receives every field and artifact plus the exact blocking action, and the
   overall release remains explicitly blocked rather than being called done.
10. The canonical `/releases/` source and deployment mirror name the GitHub
    release and report each Apple/Play channel as available, processing,
    pending owner action, or rejected from observed evidence—never from intent.
11. The Google Play handoff includes validated English listing copy, a 512×512
    icon, 1024×500 feature graphic, and genuine release-build phone and tablet
    screenshots with recorded dimensions, hashes, and provenance.
12. The exact release commit, derived build number, tag target, artifact
    hashes, signing identities, and post-upload delivery identifiers form one
    fail-closed evidence chain. The final build number must exceed Apple build
    999 and every observed Play version code.

## Artwork Risk Decision

The selected icon closely reproduces recognizable Banksy flower-thrower
artwork. This creates avoidable copyright, trademark, store-review, and future
replacement risk. The owner selected this icon after the risk was presented.
The repository and release notes must not claim ownership or a license that has
not been evidenced. A store rejection on this ground is not grounds to bypass
review; the recovery is an original replacement icon and a new build. The
recorded owner selection is the artwork go/no-go decision for technical
preparation, but any Console rights attestation remains an owner-only action.

### Out of scope

- Changing application behavior unrelated to the icon or release.
- Bumping the marketing version to 0.1.2.

- Accepting store contracts, export classifications, content-rating
  attestations, or other legally attributable declarations for the owner.
- Publishing an unnotarized DMG or an unlaunched Android release.

## Source Isolation and Candidate Identity

Implementation occurs in an isolated branch/worktree created from merged
`main`. The existing `riot-wt-icon` changes are source material only; they are
copied into the new branch after tests establish the expected contracts.
Nothing is committed in the dirty main checkout or directly in another
agent's worktree.

The final release candidate is the merge commit of the implementation PR. All
release scripts run without `ALLOW_DIRTY=1`. The scripts derive Apple build
numbers and Android `versionCode` from that commit count, so all artifacts
identify the same source state.

## Components

### 1. Cross-platform icon set

The canonical visual source is the selected 1024×1024 RGB PNG from the icon
worktree. Platform outputs are:

- `apps/ios/Riot/Assets.xcassets/AppIcon.appiconset/AppIcon-1024.png`;
- `apps/macos/Riot/AppIcon.icns`;
- Android `mipmap-{mdpi,hdpi,xhdpi,xxhdpi,xxxhdpi}` legacy, round, and
  foreground PNGs;
- Android adaptive icon XML under `mipmap-anydpi-v26` plus themed-icon XML and
  monochrome alpha mask under API-33-qualified resources; and
- Android launcher background color resources.

Android manifest references must resolve for both regular and round launchers.
The full-color adaptive foreground remains in the API-26 adaptive icon. A
separate single-color alpha-mask drawable is referenced only from API-33
adaptive icon resources for Android themed icons; it never reuses the opaque
full-color square. Tests inspect resource existence, image dimensions,
manifest references, API-qualified adaptive-icon XML, and alpha-mask structure
before Gradle packaging is allowed.

Visual review covers the canonical art at 16, 32, 48, and 64 pixels and under
iOS squircle, macOS rounded-square, Android circle/squircle, and Android themed
icon masks. The review records screenshots rather than inferring suitability
from file dimensions.

### 2. Public support surface

`marketing/support/index.html` is the editorial source.
`marketing/public/support/index.html` is its byte-identical deployment mirror.
The page provides:

- an accessible `mailto:support@protest.net` private-support action;
- a separately labelled link to public GitHub issue reporting;
- a warning not to post private keys, invitation material, or sensitive
  incident details in public reports;
- a prototype-status statement without a guaranteed response-time promise;
- links to privacy, releases, documentation, and open-source information; and
- the same dependency-free, no-analytics, accessible visual shell as the
  existing marketing pages.

The sitemap, README, live verifier, route inventory, footer contracts, and
source/public mirror contracts expand from nine to ten editorial routes.
Browser checks cover keyboard focus, narrow screens, forced colors, reduced
motion, no JavaScript, no cookies/storage, and no off-origin requests. Live
checks additionally assert CSP, Referrer-Policy, `nosniff`, and framing
protection on `/support/`.

### 3. Canonical store listing

Both stores use the approved product decisions above. Existing release
worksheets supply:

- no developer data collection;
- no ads, tracking, or developer analytics;
- user-directed nearby peer and followed-site communication;
- Bluetooth, local-network, notification, camera, and Android INTERNET
  justifications;
- Teen-equivalent content rating; and
- the implemented cryptography inventory.

The generated answers are preparation evidence, not authorization to make legal
attestations. Human-action fields remain visibly marked until the owner
confirms them in each Console.

The production listing package is canonical under
`release/store-listing/google-play/`:

- `en-US/name.txt`, `short-description.txt`, and `full-description.txt`;
- `graphics/icon-512.png` and `graphics/feature-graphic-1024x500.png`;
- at least two `screenshots/phone/*.png`, two
  `screenshots/tablet-7/*.png`, and two `screenshots/tablet-10/*.png`,
  captured from the release APK at declared emulator profiles rather than
  fabricated device UI; and
- `manifest.json`, recording locale, intended Console field, dimensions,
  source/capture provenance, and SHA-256 for every item.

Tests fail on missing required fields, store character-limit violations,
incorrect image dimensions/modes, duplicate or placeholder screenshots,
unapproved external assets, or manifest/hash drift. The handoff records each
Console field and upload result.

### 4. Android signing topology

The existing `~/riot-release-key.jks` remains the **upload key** and signs the
AAB plus a local smoke-test APK. It is not treated as the public app-signing
identity.

For the first Play release, use Play App Signing with a Google-generated app
signing key. After Play processes the candidate AAB, download Play's signed
universal APK from the bundle explorer and use that APK for GitHub direct
download. This makes Play and GitHub installs share the same app-signing
identity and preserves cross-channel updates. The locally signed APK is never
published.

Before publication, record and verify both distinct certificate fingerprints:
the existing upload certificate and Play's app-signing certificate. If the
owner instead chooses to transfer an existing app-signing key to Google, stop
and revise this design before enrollment; do not make that irreversible choice
ad hoc in Console. The upload keystore requires an encrypted offline backup,
restricted access, and a documented recovery check before first submission.

### 5. Release scripts and credentials

The merged 0.1.1 release scripts remain the build entry points and run
sequentially because they share generated FFI and native-library directories.
No credential values are committed.

Apple runtime credentials:

- key ID `M95U99RZY4`;
- Issuer ID supplied out of band at release time;
- private key already under `~/.appstoreconnect/private_keys/`; and
- Developer ID Application certificate already in the login keychain.

The key/Issuer pair has successfully authenticated to Apple's notarization
history. Build/upload commands receive it through process-local environment
variables.

Android runtime credentials:

- keystore `~/riot-release-key.jks`;
- alias `riot`;
- password from the macOS keychain; and
- expected upload certificate SHA-256
  `8552c62a629638292884aafb2431fde89032210c606c2be44d766cf8daeac084`.

Credential files must be mode 0600, shell tracing/environment dumps are
forbidden, store credentials are least-privilege, and Gradle signing runs
without a persistent daemon. Cleanup runs on every exit path. Packaged-artifact
scans reject embedded key material, passwords, environment files, or local
credential paths.

### 6. Delivery coordinator

There is no new monolithic release program. Existing small tools remain
responsible for one boundary:

- marketing tests and Wrangler own support deployment;
- `scripts/android-release.sh` owns Android build/signature verification;
- `scripts/testflight-release.sh` owns iOS archive/export/upload;
- `scripts/macos-release.sh` owns Mac App Store and Developer ID channels;
- `gh release` owns GitHub assets; and
- Play Console owns the first Android app record and legal declarations.

This preserves independently understandable failure boundaries.

## Release Data Flow

1. Approved source changes merge to `main`.
2. A clean release worktree checks out the merge commit. Every entrypoint
   rejects any repository-wide tracked or untracked change and rejects a HEAD
   that differs from the explicit approved release SHA.
3. Marketing tests pass; Wrangler deploys the exact `marketing/public` tree.
4. Live verification proves `/support/` and all other routes.
5. Android release script generates net-enabled bindings and both native ABIs,
   then Gradle builds and signs AAB/APK.
6. Signature and icon checks pass; the APK is installed and launched; logs are
   checked for FFI/native load failures.
7. iOS release script regenerates net-enabled bindings/native core, archives,
   exports, validates icon/signing, and uploads the IPA.
8. macOS App Store channel builds the universal binary, archives, exports, and
   uploads the PKG.
9. macOS Developer ID channel builds the same source, notarizes the app and
   DMG, staples both, and verifies Gatekeeper acceptance.
10. The owner completes the Play Console creation/legal gate; the exact AAB and
    canonical listing are submitted to a staged production rollout.
11. Play's processed universal APK is downloaded and its app-signing
    certificate, contents, install, and launch are verified.
12. Tag `v0.1.1` is created at the exact release SHA. GitHub publishes the DMG
    and Play-signed universal APK with checksums and release notes, then the
    downloaded public assets are verified against the recorded hashes.
13. `/releases/` is updated and redeployed from observed channel states.

The implementation PR includes the release page with known URLs and every
unpublished channel labelled pending. If observed states change only after the
binary candidate is built, a status-only follow-up PR updates those labels; it
does not alter the release tag or candidate commit.

## Test-Driven Development

Tests are written and observed failing before asset/page implementation:

1. `scripts/release/test/public-release-contract.test.mjs` first fails for
   absent Android manifest launcher references, density assets, API-26/API-33
   adaptive XML, monochrome alpha mask, listing files, asset dimensions,
   character limits, provenance manifest, and release-script whole-repository
   cleanliness/SHA checks.
2. `scripts/marketing/protocol-page-contracts.mjs` and
   `scripts/marketing/test/verify-live.test.mjs` first fail for missing
   `/support/`, unequal source/public bytes, support/private-report language,
   stale `/releases/` state, absent footer links, and the ten-route
   sitemap/live inventory.
3. Minimal fixtures are generated in temporary directories; release scripts
   accept injectable repository/status and artifact-inspection commands in
   tests rather than real credentials. Existing browser helpers remain the
   accessibility, dependency, remote-request, cookie, mirror, and route
   guardrails.
4. Each slice follows an explicit RED (capture the focused failure), GREEN
   (smallest asset/page/script change), REFACTOR (remove duplication without
   changing the passing assertion) cycle. The implementation plan must name
   each command and captured assertion.

After implementation:

- targeted release and marketing tests pass;
- Android host-JVM tests and lint pass;
- shell syntax and ShellCheck pass for release entry points;
- Rust fmt, Clippy, workspace tests, contract validation, and the exact
  composite coverage gate pass;
- the mandatory independent review reports no Critical or Important findings;
  and
- CI passes on the PR before merge.

## Artifact Verification

### Android

- Confirm AAB and APK exist.
- Verify local smoke-test APK signature and exact upload certificate SHA-256.
- Verify AAB JAR signature with `jarsigner -verify -strict -certs` and exact
  upload certificate SHA-256.
- Inspect packaged launcher resources.
- Inspect the manifest for unexpected debuggable, cleartext, backup, exported
  component, or permission changes.
- Install the local release APK on clean API-35 arm64-v8a hardware/emulation
  and x86_64 emulation when available. Launch
  `net.protest.riot/.MainActivity`, assert a live process within a bounded
  window, and retain filtered logs for missing library, UniFFI symbol,
  signature, ANR, and startup exceptions.
- Repeat signature, content, clean-install, and launch checks on Play's
  universal APK before it becomes the GitHub asset.

### iOS

- Confirm archive/export success and App Store provisioning.
- Inspect the archived asset catalog/application metadata for the selected
  icon.
- Verify the exact TeamIdentifier, certificate class, provisioning profile,
  entitlements, and absence of unexpected embedded credentials.
- Validate/upload the IPA with App Store Connect credentials.
- Record delivery/build identifiers and processing status without claiming
  TestFlight availability before Apple processes the build.

### macOS App Store

- Confirm universal arm64/x86_64 app binary.
- Confirm App Store distribution and installer signing.
- Confirm category and dSYM.
- Inspect the archived `.icns`.
- Validate/upload the PKG and record delivery status.

### macOS direct download

- Confirm Developer ID signing and hardened runtime.
- Notarize and staple the app before packaging.
- Build, notarize, and staple the DMG.
- Run `spctl`, `codesign`, `stapler`, and architecture verification.
- Never publish a DMG whose notarization or Gatekeeper check is incomplete.

For every channel, record the canonical icon-source hash, packaged icon hashes,
artifact hash, explicit release SHA, and derived build/version code before
upload. Immediately before upload, compare that number with the latest observed
App Store Connect build and Play version code.

## External and Human Gates

### Apple

Binary upload and notarization are automated. App Store Connect may still
require export-compliance, beta-review, agreements, tax, trader-status, or
other account-owner actions. Those are reported with the exact screen/status;
they are not guessed or accepted by automation.

### Google Play

Google requires the initial app record to be created in Play Console. The
current machine has an active `gcloud` user but no Play-linked service account
or Android Publisher credentials. Therefore the implementation prepares every
artifact and field but does not pretend that generic Google Cloud
authentication can create or publish the Play application.

The owner must:

1. create the free app record for `riot.protest.net`;
2. accept Play App Signing with the Google-generated app-signing key and the
   existing keystore retained as upload-only, plus the legal declarations;
3. confirm content rating, data safety, target audience, and availability; and
4. upload/submit the supplied production AAB, or link a service account with
   production release permission for subsequent automation.

The production rollout starts staged at 5%. It expands only after a 24-hour
observation window has no release-attributable launch failure, native/FFI load
failure, material crash/ANR regression, signing mismatch, or severe support
report. This remains the production track, not a testing track.

## Failure Handling and Recovery

- Dirty tree: stop; rebuild from the merged commit.
- Shared release lock exists: stop; identify the active/stale owner before
  removal.
- Icon contract fails: stop; regenerate from the canonical source.
- Support deployment/live verification fails: stop before store submission.
- Signing identity/certificate mismatch: stop; never resign with a new key.
- APK install/launch fails: diagnose the release binary; do not submit AAB.
- Apple upload rejected: retain the exact archive and delivery log; fix root
  cause in a new reviewed commit/build.
- Apple processing or legal gate pending: report pending, not released.
- Notarization or Gatekeeper failure: do not publish the DMG.
- Existing GitHub `v0.1.1`: inspect and update intentionally; never create a
  duplicate or overwrite unrelated assets.
- Play Console blocks submission: preserve the exact AAB and prefilled
  worksheet; hand off the precise unresolved human action.

If a defect or compromise is discovered after publication:

- pause the Play staged rollout immediately; unpublish only with owner
  authorization, because existing users retain the installed build;
- expire/remove the affected TestFlight build from testing;
- move the GitHub release back to draft or withdraw the affected assets with
  owner authorization, publish a clear warning, and retain hashes/evidence;
- roll Cloudflare back to the recorded prior deployment and verify the live
  routes;
- build a reviewed higher build/version code forward fix—never overwrite a
  store build or silently replace an asset under the same checksum;
- revoke/rotate a compromised App Store Connect key, Developer ID certificate,
  upload key, or console credential through the relevant provider, while
  preserving the Play app-signing identity; and
- document scope, first/last known exposure, affected hashes, containment time,
  owner decisions, and the safe replacement path.

## Release Evidence

The final handoff records:

- source merge commit;
- version/build numbers;
- artifact paths, sizes, and SHA-256 checksums;
- Apple delivery/notarization identifiers and states;
- Android upload and Play app-signing certificate fingerprints;
- APK install/launch evidence;
- live support URL verification;
- store-listing manifest and screenshot capture profiles;
- GitHub release URL and asset names;
- Play Console state and exact remaining human action;
- prior/current Cloudflare deployment identifiers plus channel rollback state;
- public-channel observation results; and
- all red/green test history relevant to the candidate.
